# プロダクト説明書：onsite

## 一言で

誰かがその場所に残した投稿を、**実際に近づいたときだけひらける**、おでかけと観光のための SNS。

## 誰の、どんな課題か（Why）

- **課題**：SNS で街や旅先の面白い場所を見ても、写真を見た時点で満足してしまい、実際に行くことは少ない。観光情報も「有名な場所」に偏り、地元の人が知っている小さな発見は外に伝わりにくい。
- **対象**：街歩きや旅行が好きな人、知らない街を訪れた観光客、その街の小さな面白さを知っている地元の人、祭りや商店街・学園祭のように「回ってほしい場所」がある主催者。

## どう解決するか

- 地図には投稿の **予告だけ** を出す（例：「宝蔵門の裏側を見たことある？」）。
- 本文と写真は、投稿者が決めた範囲（100m・300m・500m・1km）に **入った人だけ** がひらける。判定はサーバーで行う。
- 範囲に入った瞬間に知らせ（端末の振動と「SIGNAL IN RANGE」）が出て、その場でひらける。
- ひらいた人だけが書ける **寄せ書き** と **いいね** で、同じ場所に来た人どうしがつながる。
- 投稿をつないだ **イベント（巡りルート）** に、開催期間（いつでも・今日・3日間・1週間）を付けられる。祭りやツアーの「この期間だけの巡り」を誰でも作れ、全部ひらくと制覇の演出が出る。
- 自分の **足あと** と、みんなの **踏み跡** が地図に残る。

## なぜこの方法か（Intent）

- **予告を遠くから見せる**のは、目的地を選んで出かけられるようにするため。存在ごと隠すと、どこへ行けばいいか分からず、投稿が少ないうちは何も起きない。
- **範囲を投稿者が選べる**のは、「この角度から」のようなピンポイントの発見と、「この川沿い」のような広い発見の両方を扱うため。
- **寄せ書きをひらいた人だけに限った**のは、「その場所に行った人だけの会話」にすることで、行く理由をもう一つ作るため。荒らしや先読みも防げる。
- **イベントは誰でも作れる**。主催者だけでなく、旅行者が「自分のおすすめの回り方」を共有できるようにするため。期間を付けられるのは、祭り・展示・期間限定の催しに合わせるため。
- **判定はサーバー（Cloud Functions）で行い**、本文・写真・寄せ書きはブラウザから直接読めないようにした（Firestore のルールで遮断）。開発者ツールを開いても先に読めない。
- **地図を「立体の地形模型」にした**のは、旅先で「どの建物の、どの角か」が分かるようにするため。平面の地図より、実際に立ったときの景色と結びつく。見えている範囲の外側をブロック状に闇へ沈めているのは、情報を絞って「ここから先は歩いて確かめる」感覚を出すため。

## 見た目と体験の方針

- 地図は Google の立体地図（Photorealistic 3D Tiles）を、自作の画面効果で「地形模型を映す端末」のように見せている（実写の色を少し落とし、陰影を強め、外周をブロック状に欠けさせ、深い紺の闇に格子を引く）。
- 道のり・巡りルート・範囲の線は「レーザー」として描く（白い芯と色のにじみ、進む向きに光の粒が流れる）。
- 自分の現在地には、オスカー像のような **トロフィー像のアバター** が立つ。体型（紳士・レディ・ドレス・ゴブリン）、ポーズ、仕上げ（ゴールド・シルバー・ローズゴールド・クリスタル）を最初の画面で選べる。像は Blender をスクリプトで動かして作った自作のモデル。
- 文字は細く字間の広い英字と日本語の組み合わせ、箱をなるべく使わず光の帯と細い線で区切る。投稿を読む画面は写真を大きく、読み物として落ち着いて読めるようにした。
- スマホでは下にタブ、選んだ投稿は下から出るシートになる。

## 主な機能

1. 地図の照準で場所を選び、予告・本文・写真・範囲を決めて投稿
2. 地図に予告を六角形の印とラベルで表示（未開封・ひらける・開封済み・自分の投稿で色と記号が変わる）
3. 現在地との距離を表示。範囲に入ると知らせが出て、ひらける（はじめては開封の演出）
4. 寄せ書き（コメント）といいね（ひらいた人と投稿者だけ）
5. フィード（まわりの予告。近い順・新着順）
6. イベント（投稿をつないだ巡りルート、開催期間、参加、進み具合、制覇の演出）
7. 自分の足あと、みんなの踏み跡（共有は初期設定でオフ）
8. 経験値とレベル、お知らせ
9. デモモード（現地に行けない人が、地図をタップして移動できる。開始地点は浅草）
10. 軽い版（立体地図が重い端末向けに、同じ機能を平面地図で使えるウェブ版）

## 使っている技術

| 層 | 技術 |
| --- | --- |
| アプリ本体 | Unity 6（C#）、URP、UI Toolkit。WebGL（ブラウザ）と Android に書き出し |
| 立体地図 | Cesium for Unity ＋ Google Photorealistic 3D Tiles（Map Tiles API） |
| 画面効果 | 自作のシェーダー（地図の画面効果、レーザーの線） |
| 通信 | Firebase の REST API を C# から直接呼ぶ（Authentication・Firestore・Storage・Cloud Functions）。Firebase の Unity SDK はブラウザ向けに書き出せないため |
| サーバー | Cloud Functions for Firebase（TypeScript）：開封判定、投稿、寄せ書き、いいね、イベント、踏み跡 |
| 公開 | Firebase Hosting（ブラウザ版）。軽い版は React ＋ Vite ＋ Google Maps JavaScript API |
| 3D モデル | Blender（Python スクリプトで生成） |

## 技術の選び方と、その代わりに諦めたこと（トレードオフ）

- **Unity を選んだ理由**：立体の地形、画面全体の効果、光る線、3D のアバター、演出を、同じ仕組みの中で思いどおりに作れるため。最初はウェブ（React と Google Maps）で作ったが、地図の見た目と演出の自由度が足りず、「出かけたくなる」体験にならなかった。
- **諦めたこと**：
  - 読み込みが重くなった（初回はおよそ 17MB に加えて地図のデータ）。古い端末のために「軽い版」を残し、読み込み画面から切り替えられるようにした。
  - Firebase の Unity SDK が使えないため、認証と通信を REST で書き直した。手間は増えたが、ブラウザとスマホで同じコードが動く。
  - ブラウザでは複数スレッドを使うため、配信時に特別なヘッダー（COOP/COEP）が必要になった。Firebase Hosting の設定で対応した。
- **判定をサーバーにした理由**：ブラウザ側で判定すると、通信を見れば本文が読めてしまう。GPS 自体は偽装できるので「現地にいた証明」には使わず、「その場で読む体験」を守るための仕組みと位置づけた。

## AI をどこで、どう、なぜ使ったか

- **Claude Code（Anthropic）**：全体の設計、作業の分担と指示、シェーダー（地図の画面効果・レーザー）、地図と線の処理、サーバーの関数、ビルドと配信、動作確認、説明書の下書きに使った。人（作者）は、作るものの方向性（「近づくと読める」「デス・ストランディングの地図のような見た目」「アカデミー賞の像のようなアバター」など）を決め、出来を見て何度も作り直しを指示した。
- **Codex（OpenAI）**：Claude Code の指示で、並行して次を担当した。Firebase の REST 通信層（C#）、画面（UI Toolkit）の作成と作り直し、Blender でアバターを作るスクリプト。担当するフォルダを分け、互いの作業がぶつからないようにした。
- **なぜ使ったか**：一人で、限られた時間で、ウェブ版から Unity 版への作り直しまで行うため。AI が出したものは、毎回ブラウザで動かして確かめ、合わないものは捨てて作り直した（例：地図の見た目は参照画像と比べて何度も作り直した）。
- **AI に任せなかったこと**：何を作るか、誰のためか、どこで妥協するか（軽い版を残す、GPS を証明に使わない、など）の判断。

## 安全とプライバシー

- 現在地は距離の判定にだけ使い、サーバーには保存しない（開封時の距離だけを本人の記録に残す）。
- 投稿の場所は地図の照準で選ぶ方式にし、自分の現在地のすぐそばに置こうとすると注意を出す。
- 自分の足あとは端末の中だけに保存する。みんなの踏み跡への共有は初期設定でオフで、共有してもマス目ごとの回数にまとめ、個人の移動はたどれないようにした。
- ログインは匿名。名前はニックネームだけ。
